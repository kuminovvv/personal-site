# 04. Компоненты

## 1. Базовые правила

Каждый компонент:
- использует именованный экспорт;
- по возможности имеет отдельный типизированный контракт;
- соблюдает правило `один файл = один компонент`.

## 2. Типы и `types.ts`

Выносить типы в `types.ts`, если:
- компонент нетривиальный;
- есть несколько связанных типов;
- контракт должен быть читаем отдельно от реализации.

### Суффиксы типов:
- `Props` (например, `ProductCardProps`)
- `Component` (например, `ProductCardComponent`)
- `Hook` (например, `useProductCardHook`)

---

## 3. Деструктуризация пропсов

**Обязательно:**
- Всегда деструктурировать пропсы через `const { ... } = props` в начале компонента.
- Каждое свойство указывать на отдельной строке.
- Дефолтные значения указывать прямо в деструктуризации.

```tsx
// ✅ Правильно
export const Chart: ChartComponent = (props) => {
  const {
    data,
    width = 800,
    height = 600,
    showGrid = true,
    onPointClickAction
  } = props;

  // ...
};

// ❌ Запрещено — деструктуризация в аргументах
export const Chart = ({ data, width = 800 }: ChartProps) => { ... };

// ❌ Запрещено — использование props.* в JSX
return <svg width={props.width} height={props.height} />;
```

---

## 4. `Action`-handlers (TS71007)

Если функция передается через props в `"use client"` компонент, имя должно заканчиваться на `Action` (чтобы избежать ошибок сериализации Next.js).

Пример:
```ts
type ModalProps = {
  onCloseAction: () => void
}
```
*Примечание: обработчики нативных DOM-событий прямо в JSX (например, `onClick`) могут оставаться обычными.*

---

## 5. Структура файла компонента

Допустимы только:
1. Импорты (React → внешние библиотеки → проектные модули → локальные импорты).
2. Собственный тип props.
3. Один компонент с именованным экспортом (для Next.js route files — обязательный default export).

В теле компонента: деструктуризация props, вызовы хуков, вычисления из props/state,
связанные обработчики и JSX. Независимые функции нельзя прятать в теле компонента
ради обхода правила.

## 6. Константы и данные

Статические массивы, словари переводов, варианты стилей, конфигурации и константы
размещайте в отдельных `.ts` файлах `model/` или `lib/` слайса. Переиспользуемые
модули размещайте в `shared/lib`. Варианты оформления общих UI-примитивов допустимо хранить в отдельных `.ts` файлах `shared/ui`. Файл компонента только импортирует их.

## 7. Логика и исключения

Самостоятельные helpers, type guards, подписки и пользовательские хуки храните
отдельно от компонента. Сложное управление состоянием и жизненным циклом выделяйте
в хуки `model/`. В файле компонента не должно быть нескольких независимых обязанностей.

Исключение — обязательные экспорты Next.js в `page.tsx`/`layout.tsx`:
`metadata`, `viewport`, `generateMetadata`, `generateViewport`, `generateStaticParams`
и поддерживаемые настройки маршрута. Произвольные вспомогательные объявления этим
исключением не разрешаются. `dynamic`, `memo` и `forwardRef` считаются объявлениями
компонента; такой компонент также должен быть единственным в файле.

---

## 8. React imports

Использовать именованные импорты для хуков и типов:
```ts
import { useEffect, useState } from 'react'
import type { FC, ReactNode } from 'react'
```
*Разрешается `import React from 'react'` в не-клиентских файлах хелперов/хуков для предотвращения ошибок TypeScript "Referenced UMD global variable", если используются глобальные пространства имен, такие как `React.Dispatch` или `React.SetStateAction`.*

---

## 9. Ограничение размера и декомпозиция

* **Компонент**: Максимум 200–250 строк. При превышении разделяйте на подкомпоненты.
* **JSX вложенность**: Максимум 4 уровня вложенности.
* **Признаки для разделения**:
  * Более 3–4 состояний `useState`.
  * Более 5–6 эффектов `useEffect`.
  * Более 10 обработчиков событий.
